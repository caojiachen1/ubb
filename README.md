# UBB — Universal Browser Bridge

A browser extension that lets any AI agent (CLI tools, scripts, coding assistants) control the user's real, logged-in browser: open pages, click, fill forms, scrape content, take screenshots, watch console/network — through a local daemon over an authenticated WebSocket.

## Key features

- **106 tools** in 11 categories (full list below): navigation, interaction (ref / CSS selector / coordinates, driven by real CDP input), accessibility-tree snapshots (paginated, hover-probing, **child frames included**), screenshots / element shots / full page / **PDF**, structured table & list extraction, site-aware page rules (github / zhihu / juejin / wechat / xiaohongshu / x.com) that are now **data, not code**, user-action recording **plus a trace replayer that needs no LLM**, pull-mode live screencast, console & network capture, download ledger, audit trail, whitelisted raw CDP, performance tracing, emulation, batch content fetch, clipboard, history, human-assistance requests, and a local **credential vault**.
- **Iframes are in scope**: the content bridge is injected into every frame (`all_frames`), `snapshot` appends each child frame as an indented `# frame[N]` section with its own refs, and actions on a frame element are dispatched at the element's **top-viewport coordinates**. That coordinate path reaches the **main document and same-process child frames only** (cross-origin, same-site — the page's own `isTrusted=true` record is what distinguishes them). A cross-site **out-of-process frame (OOPIF) receives nothing** from a page-level debugger session's `Input.*`: the gate opens, the coordinates are right, the frame logs zero events. Those targets are therefore refused up front with `FRAME_UNSUPPORTED` — never an `ok:true` that lands nowhere. The MV3 boundaries are spelled out in [Iframes](#iframes); do not discover them by guessing.
- **Coordinate input is gated on proof, not on hope**: before any mouse/key action the shield's overlay must *provably* step aside for that specific frame at that specific point (addressed `UBB_PASS` + a DOM read-back). If it cannot, the call aborts with `SHIELD_PASS_FAILED` and **not one mouse or key event is put on the CDP wire**. This is a tightening: until this batch the same situation returned `ok:true` (`{"clicked":"@e29", …}`) while the page received nothing at all. *(offline-proven, awaiting a real-browser re-check — see [Verification status](#verification-status))*.
- **A visible document, or no input at all**: a trusted pointer/keyboard action additionally asks the target document's own `document.visibilityState` **before dispatching** — a tab in a minimized or covered window (and `tab.select` does not fix that) cannot receive one, so it is refused up front with `INPUT_NOT_DELIVERED` and zero events sent instead of burning a ~7 s proof budget on a queue that never drains. The refusal names the exits that actually exist (user raises the window · `tab.create {"url":…,"active":true}` · the `@d` bridge path, `isTrusted:false` and *not* equivalent). Sensing, screenshots, extraction, diagnostics and the bridge paths keep working in the background. *(offline-proven, awaiting a real-browser re-check — see [Verification status](#verification-status))*.
- **You can tell which build is actually answering**: the extension reports its `BUILD` in the WebSocket `hello`, and `ubb status` / `/health` surface it as `extension_build` next to the daemon's own version. `extension: true` only ever proved *something* is connected — never that it is the code you just edited. *(wired and checked on a scratch port; the field only appears once both halves run this batch's code, so a daemon or extension you have not restarted will still not show it)*
- **Replay**: `record_stop` yields a semantic trace and `replay` re-matches every event against a *fresh* snapshot (role + name scoring, selector as tie-breaker) before driving it — `dry_run:true` prints the plan and touches nothing. `replay.save/list/run/delete` keep named scripts in `chrome.storage.session` (lost on browser restart).
- **Credentials never enter the model's context**: values live in `~/.ubb/secrets.json` (created by `ubb secret add`, read from stdin); a tool call carries only a *name*. What was relaxed and what is still hard-refused: [密钥与自动化边界](#密钥与自动化边界).
- **Session = tab group**: agent tabs are auto-grouped under a "⏳ UBB" tab group with status emoji. No separate window. Tabs open silently in the background — the user is never switched away from what they are reading (opt in with `active:true`, or `session.start {"own_window":true}` for a dedicated agent window). Taking over an existing tab requires an on-page Allow/Deny banner (60s, default deny).
- **Shield on controlled tabs**: pulsing border + input blocking (clicks, keys, wheel, touch) with a one-click "Stop agent" interrupt. Input blocking now also covers iframes (`content/frameblock.js` runs `all_frames`); the border is drawn in the top document only. Hidden automatically during screenshots and PDF renders. The blocking layer is a fixed full-viewport shadow host at the maximum z-index, so *the agent's own injected input crosses it only inside a pass window that has been confirmed frame-by-frame* — an unconfirmed pass aborts the action instead of having the veil swallow it silently.
- **Security by default**: token-authenticated loopback WebSocket (extension dials out only — it never listens), restricted pages blocked at both ends of the URL pipeline, destructive actions require explicit `confirm:true`, results are redacted (passwords, tokens, cookies, sensitive URL params), every action lands in an in-memory audit ring whose sequence numbers survive service-worker restarts.
- **For the human watching**: `ubb audit tail --follow` drains the audit ring to `~/.ubb/audit/<day>.jsonl`, `ubb audit stats` summarizes per-tool call counts/errors, and `ubb liveview` serves a loopback-only JPEG page of what the agent is actually seeing.
- **Experimental human mode** (default off): bezier mouse paths with jitter and dwell, per-key typing cadence with occasional typo+backspace, chunked scrolling.
- **Zero dependencies, zero telemetry**: no npm install anywhere — the daemon, the Node CLI and the MCP adapter are plain Node (≥18/22), and nothing is sent anywhere except to your own local daemon.

## Architecture

```
AI agent (any process)
  ⇅ newline-delimited JSON-RPC over stdio, or WebSocket
ubb-bridge.mjs (daemon, 127.0.0.1, token auth)
  ├─ daemon/cli/*.mjs       extra subcommands (secret / audit / liveview / download)
  └─ daemon/mcp-tools/*.mjs curated ubb_* MCP catalog (+ ubb_call fallback)
  ⇅ ws://127.0.0.1:<port>/  — extension connects out, never listens
UBB extension (MV3 service worker)
  ├─ chrome.debugger (CDP)  — page control, one session per tab
  ├─ lib/tools.js + lib/tools-*.js — the tool registry (via lib/tools-extra.js)
  ├─ content scripts — shield (top frame only), bridge + site-rule engine (all frames),
  │                    frame input blocker (all frames), foreign-frame monitor
  ├─ content/site-rules.json — packaged extraction rules (user overrides in storage.local)
  └─ offscreen document — clipboard
```

Tool count and per-tool metadata are not folklore: `node -e "import('./lib/testharness.mjs').then(h=>h.collectRegistry().then(r=>console.log(r.names.length)))"` prints **106**, and `daemon/test-fill.mjs` asserts that every registered tool carries a description.

## Install

See [INSTALL.md](INSTALL.md). Summary:

1. Load the unpacked extension from this folder (`chrome://extensions` → Developer mode → Load unpacked).
2. Copy the pairing token from the extension popup — or run `bin/ubb install` once and skip token copying entirely (native-messaging auto-pair).
3. Start the daemon: run `ubb status` (auto-starts it), or manually: `node daemon/ubb-bridge.mjs --port 8765 --token <token>`
4. Verify: `ubb status` → `"extension": true` **and** `"extension_build"` equal to the `BUILD` constant in `lib/config.js`. `extension: true` alone only proves *something* is connected — `extension_build` is what proves it is *this* code. If the key is missing entirely, the daemon answering you is an older process (restart it); if the value is a stale string, the extension was never reloaded. This one check is worth the thirty seconds: a live session was once lost for half an hour to exactly that ambiguity, and a daemon that has been up for two days quietly runs two-days-old code.

## Quick start

```bash
ubb list                                  # tool catalog (106)
ubb tab.create '{"url":"example.com"}'
ubb snapshot                              # accessibility tree with @eN refs (+ # frame[N] sections)
ubb click '{"ref":"@e3"}'
ubb screenshot --out shot.png
ubb session.stop

# new in this batch
ubb snapshot                              # then: ubb frames.probe   (what this build really supports)
ubb dropdown_options '{"ref":"@e9"}'      # options of a closed <select> / combobox
ubb print_pdf --out report.pdf            # CDP Page.printToPDF, shield hidden
ubb search '{"query":"ubb mv3 iframe"}'   # SERP in a new session tab (nothing is parsed)
ubb replay '{"trace":"…","dry_run":true}' # plan only — no input is dispatched
ubb download list                         # then: ubb download cat 42
ubb audit tail --follow
ubb liveview                              # http://127.0.0.1:8790 — for the human
ubb secret add github_pw                  # value from stdin, never from argv
printf '%s' '{{secret:github_pw}}' ; ubb fill '{"ref":"@e7","value":"{{secret:github_pw}}"}'

# No Rust CLI on PATH? The Node CLI takes the same commands (Node >= 18):
#   node daemon/ubb.mjs <command>
```

Any agent that can spawn a process can use it: pipe JSON-RPC lines to the daemon's stdin, or connect as a WebSocket agent (`ubb-agent.<token>` subprotocol).

## MCP (backup interface)

For MCP-capable IDE agents (Qoder, TRAE, Cursor, …) that prefer typed tools over shell, `daemon/mcp.mjs` is a zero-dependency MCP stdio adapter speaking to the same daemon — session state is shared with the CLI, and the CLI + skill stay the primary interface:

```bash
node daemon/mcp.mjs                       # stdio MCP server (Node >= 22)
```

IDE MCP settings (Qoder: Chat MCP settings · TRAE: 设置 > MCP — both take a stdio JSON config):

```json
{ "command": "node", "args": ["D:/Codebase/ubb/daemon/mcp.mjs"] }
```

The catalog is **52 tools: 51 curated `ubb_*` + the universal `ubb_call {tool, params}`** that reaches the full 106-tool registry (count from `daemon/mcp-tools/index.mjs`; a new tool does not have to be curated to be reachable). Token/port resolve exactly like the CLI (`UBB_TOKEN`/`UBB_PORT` env > `~/.ubb/config.json`), and the daemon is auto-started if missing. Binary results are saved rather than inlined: screenshots go to `~/.ubb/shots/*.png|jpg` and **`ubb_print_pdf` now lands `~/.ubb/shots/*.pdf`**, returning the path (token-friendly); pass `inline:true` for a screenshot to embed the image instead. Over 3 MB a PDF comes back as `{too_big:true, bytes, filename_suggested}` and you save it with the CLI (`ubb print_pdf --out …`).

Two gates are orthogonal to this list and still apply per action: a dangerous/paid label (删除/支付/delete/transfer…) needs `confirm:true` even on `click`, and `secret.set` additionally warns that the *value you pass* enters the conversation transcript — which is exactly why `ubb secret add` in a terminal is the better route.

`secret.fill` is deliberately **not** in the gated list. `confirm:true` is something the model can type itself, so it is not a boundary — an attacker who controls the agent just sets it. What actually bounds `secret.fill` is structural: the value never appears in the agent's arguments or results, it is fetched from the daemon at typing time, a vault entry can be origin-bound (`ubb secret bind`) with `strict` mode refusing any host mismatch *before* the value is even fetched, every fill is audited with `{name, host, field_role}`, and the never-fill field classes (OTP/CVV/card/private key) are refused whatever the source.

Ref discipline: refs (`@eN`) come from `snapshot` and stay valid across snapshots and across `next_cursor` pages of the same capture; navigation invalidates them (`REF_UNKNOWN`) — take a fresh snapshot. Large pages return `next_cursor` instead of silently truncating. Frame refs are `@eN` *inside* a `# frame[N]` section (addressable; coordinate actions reach them in the main document and in same-process frames — a cross-site OOPIF ref refuses with `FRAME_UNSUPPORTED`) or `@d<frameId>.<n>` from `find`, which acts through that frame's own bridge and therefore works in an OOPIF too.

## 密钥与自动化边界

以前密码框一律拒填，现在**只放松这一件事**：口令可以由工具填了，但模型永远只能交出"名字"。你把口令用 `ubb secret add github_pw` 存进本机 `~/.ubb/secrets.json`（明文，只在你自己的用户目录里，Windows 上真正的边界是 per-user ACL + BitLocker），agent 说的是 `{"ref":"@e7","secret":"github_pw"}` 或 `{{secret:github_pw}}`；**明文由扩展在要敲键盘的那一刻向 daemon 现取现用**，不进参数、不进返回值、不进审计、不进 daemon 日志，也不进你和模型的这段对话。兜底的占位符替换只发生在 `fill` / `fill_form` 的值和 `replay` 的 `vars` 里；`evaluate`、`cdp.call`、`webmcp.invoke` **永不替换**——否则等于把钥匙交给页面上随便一段 JS，那不是"填个表单"，那是任意读走。`type` **同样不替换**（2026-10-28 实机事故后的能力收缩，LIVE-RESULTS-2B §3c：`type` 没有目标字段，没有节点可供恒拒闸门分类，替换等于把明文打进当时恰好聚焦的任何一个框——包括 OTP/CVV 框；`{{secret:NAME}}` 在 `type` 里保持字面量，要用 vault 就改用 `fill` 或 `secret.fill`）。模型伪造的 `__ubb_secret_*` 标记在 daemon 转发前先剥掉再重新盖章，`replay.save` 里如果混进了真值也会被还原成占位符再落盘。

死守的部分一行没让：`OTP / one-time-code / 验证码 / cvv / cvc / 卡号 / 私钥` 无论什么模式、什么通路（包括 vars 和 `secret.fill`）恒拒，没有任何绕过参数；密钥名里带 `secret` 的字段（如 `client_secret`）也一并拒——故意的过度保守，不是 bug。默认模式是 `off`：**未绑定 origin 的口令可以被打进任意页面的密码框**，这是 2026-10-28 明确选定的默认，代价说清楚——钓鱼页收割的是"你自己存进 vault 的那条口令 + 你正在登的那个站"，值不回传给模型，但目标页能读它自己的输入框。要把这道口收紧就 `ubb secret bind github_pw github.com` + `ubb secret mode strict`：strict 下未绑定的条目一律拒、host 不匹配一律拒，且**在取值之前就拒**。`ubb secret mode strict` 这个**单参数设值现在真的生效**了——实机验收时它只回显当前模式、一个字都不写（`strict` 被当成 secret 名吃进了解析槽位），当时靠 `ubb secret mode strict strict` 双写才落盘；那条 workaround 现在会明确报错，正确写法只有单参数一条（`ubb secret mode loose` 这类非法值同样 exit 1 并点名两个合法值；`rm`/`has` 多余参数也不再静默忽略）。这一条是 CLI 侧改动，用真 CLI + 临时 config 验过，不需要浏览器；**strict 真拒（`SECRET_ORIGIN_DENIED`、零次取值）仍未在实机上确认过**，因为 19:00 那轮的 daemon 是 10-26 的旧进程，反向 RPC 分支根本不在跑着的那份代码里。`strict` 判定按帧自己的 URL（拿不到帧 URL 时退回顶层 host，退回即拒 = fail-closed），单次调用可用 `enforce:"strict"|"off"` 覆盖。另一条要如实交代的尾巴：`localhost` 页面走 `onMessageExternal` 直连扩展 dispatcher 时**绕开 daemon 的替换点**——那条通路拿到的是原样未解密的 `{{secret:X}}` 字符串，所以它是 fail-safe（不替换就等于不解密），泄露面为零，只是不受 strict 管辖。想审计就 `ubb audit tail`，每次填充都留 `{vault_entry, origin, field_role, mode, decision}`（这一形状出自**失败样本之外的期望**，成功填充的审计字段同样待实机核对）。

## Shield and the silent-lie fix

The worst live finding of this batch was not a crash, it was a **lie**: with the shield armed (i.e. in every normal session, on every controlled tab), a coordinate action could return `{"clicked":"@e29","at":[65,299],"target":"Save batch"}` — `ok:true`, audit entry written — while the page's own log stayed empty, because the shield's full-viewport overlay was eating the injected input. The same call landed correctly the moment that overlay was hidden by hand.

The gate is now *verifiable instead of assumed* (`lib/shield-ctl.js`): every pass request is **addressed to a frame id** (no broadcast), waits for that frame's own ack, and then reads the DOM back through `chrome.scripting.executeScript` targeting the frame — forcing the veil open on every host this extension owns, and reporting whether the point still hits a shield element. Two bounded rounds, and if neither confirms, the action is **aborted before a single mouse/key event reaches CDP**, and the pass is taken back so no half-open door is left behind. The `type` / `press_key` path is stricter still, because an orphaned world's capture-phase key listener cannot be disarmed through the DOM.

`SHIELD_PASS_FAILED` means exactly that: **the overlay did not move aside, the action was aborted, and nothing was sent down the CDP wire.** Treat it as honest bad news, not as a retry-me signal — the same call repeated unchanged will fail the same way. Real exits, in the order you should try them:

1. the **"■ 停止代理"** button in the page's top-right status strip (→ paused, the veil opens immediately and the tab stays usable);
2. the popup's shield mode — `block` → `border` → `off` (a reload-free downgrade; `border` keeps the visual marker and drops input blocking);
3. **reload the extension** at `chrome://extensions` — the only cure for the orphan copy described below;
4. `tab.release` and then `tab.claim` again, which re-arms the shield from a clean state for that tab.

There is **no `shield.*` tool and no `ubb shield.mode` CLI command** — the four exits above are all that exists, and the error message only names those.

One honest exception: `cdp.call` still lets a raw `Input.*` through (it is the documented escape hatch, `confirm:true`), and that route is **not** run through the per-dispatch confirmation above — so our own overlay may still eat the event and **the tool will not confirm it for you**; the return value says so out loud (`gate_bypassed: true` + a `note`, same key in the audit). If the input has to land, use `click` / `type` / `fill` / `press_key`.

Why this could have been broken for a long time, worth knowing: `document.querySelectorAll('.ubb-host-root').length` came back **2 on a freshly created tab**. Not a duplicate manifest registration, not two installed copies — MV3 content scripts each run in their own *isolated world*, and the `window.__ubbShield` guard is world-scoped, so it cannot see a host already sitting in the shared DOM. After an extension reload (or a world teardown), the **orphaned host stays in the DOM while its `chrome.runtime.onMessage` listener is dead**: `UBB_PASS` can never reach it, and its veil stays permanently at `pointer-events:auto`. Two layers eating events, one of them unreachable — which explains both "the count is 2" and "the ack arrived and the click still vanished". `content/shield.js` now marks its host with the extension id and prunes same-owner copies (including owner-less leftovers from older builds) at build, on every state application and on every state query, so the invariant "exactly one host per document for this extension" holds continuously.

*All of this is offline-proven (`daemon/test-shield.mjs`, 138 assertions as of the fix10 run, run against the real `content/shield.js` source and a real CDP-wire trace) and **awaiting a real-browser re-check**: host-count convergence in live Edge, `executeScript` being permitted into a cross-site OOPIF, and frame-internal keyboard input. (The second item is the one the *previous* live pass — running the pre-fix build — already had to answer implicitly: an OOPIF refusal it recorded carried a host count that only that channel can produce. The other two are open.)*

### An ack is not a delivery: `INPUT_NOT_DELIVERED` (fix17–19)

The gate above proves the **door**; it did not prove the **event arrived**. CDP `Input.*` answers as soon as the command is *queued*, so a tool could still report `{"clicked":"@e29"}` while the document received nothing (live pass 6: 20/20). A pointer action now names the records it must **see in that document's own delivery ring** before the door may close, and returns `delivered:true` + `delivery_ms` on that page-side evidence — or it fails with `INPUT_NOT_DELIVERED`. No evidence, no success: the lie shape (`ok:true` with zero page records) is closed off at the return-value level, not by convention.

The second half is what that cost on a real machine (live pass 7, occluded Edge window, 20/20 + 3/3): a document whose `document.visibilityState` is not `"visible"` never drains its trusted-input queue at all — the door stayed open the whole time (`veil_at_read:"none"`), the ring stayed empty (`records_seen:0`), and every click burned **≈12.09 s** (≈5.07 s for the ack + the full 7 s proof budget) to arrive at an honest red. So since fix19 the hidden case is decided **before dispatch**: each pointer / real-keyboard action asks the target document (`chrome.scripting`, one bounded round trip, cached per `(tabId, frameId)` for 5 s and dropped on navigation/reload/`tab.select`/window state changes) and, on a non-visible answer, refuses immediately with `INPUT_NOT_DELIVERED` and **zero events on the wire** — which also means a retry cannot double-fire something the page may already have acted on.

`INPUT_NOT_DELIVERED` therefore has two distinct origins, and the `data.stage` field separates them: `pre-dispatch` (fix19 — nothing was sent; the message names the three exits: the user raises the window, because no tool call can; `tab.create {"url":…,"active":true}`, or `tab.select` **with the caveat that an occluded window stays hidden through it**; or the `@d` bridge path, labelled `isTrusted:false` and not semantically equivalent) versus the delivery-proof refusal after dispatch (fix17/18 — events went out, the document did not record them, and a press/release is **never** auto-repeated). Sensing, screenshots, extraction, network/console, downloads and the bridge paths are untouched by this rule, and a document whose visibility cannot be read is neither allowed nor refused on the strength of that guess — it walks the previous route and pays the proof budget.

**Status, in the house voice: offline-proven (`daemon/test-delivery.mjs` 53 + `test-integrate` [N] + `test-fill` [9]), awaiting a real-browser re-check of fix19 itself** — the 20/20 white-wait and the hidden/visible split it replaces are live measurements; the fast-fail that now handles them is not yet.

## Iframes

Design: **sensing goes through a bridge injected into each frame; actions go through top-viewport coordinates — and coordinate penetration is limited to the main document and same-process child frames.** The extension can compute a frame element's box in the *top* document (the `<iframe>` element belongs to its parent document, so `getBoundingClientRect` works even cross-origin; the chain comes from `chrome.webNavigation.getAllFrames`), and a page-level debugger session's `Input.*` lands in whatever document owns that box **as long as that document shares the renderer process**. A cross-site document in its own process (OOPIF) does not receive it: the events leave the wire, the frame records nothing, and the tool call used to answer `{"clicked":…}` anyway. That is now a hard refusal, not a discovery you make at runtime — **every action against an out-of-process frame target answers `FRAME_UNSUPPORTED` before a single `Input.*` is sent**, and the message names the three exits that actually exist: act through that frame's own bridge with an `@d<frameId>.<n>` ref (`click` / `fill` / `select`, in-page synthetic events — the same channel `read_page` uses, which does reach OOPIFs), let the user click, or `tab.create` the frame URL as a top-level tab. **Perception is never refused** — `read_page` / `find` / `element.info` / `screenshot` still see those frames. `content/bridge.js` and `content/frameblock.js` are `all_frames`, so a frame's DOM, snapshot labels, dropdown options and dialog handling are reachable; every outbound `chrome.tabs.sendMessage` carries an explicit `frameId` (without it, MV3 broadcasts the message to *every* frame, which would run a write op N times — a real bug this batch fixed).

Capability matrix — what does **not** work, and why:

| Situation | Behaviour |
|---|---|
| Cross-site (OOPIF) frame + a node-based op | `FRAME_UNSUPPORTED` from `upload_file` (needs `DOM.setFileInputFiles` on a CDP node) and from `ax.action {action:"setValue"\|"expand"}` (runs page JS on a node). MV3 exposes no CDP `sessionId`, so the flattened page session has no debugger channel into an out-of-process frame. `evaluate` has no frame targeting at all — it runs against the top document. |
| Cross-site (OOPIF) frame + a **coordinate** op | Also `FRAME_UNSUPPORTED`, refused **before** any `Input.*` goes on the wire, at every coordinate-input entry point: `click`, `hover`, `fill`, `fill_form`, `form.set`'s physical-click branch, `ax.action {focus\|click}`, both `drag` endpoints, and `snapshot {probe_hover}`. Reason: the gate opens, the box is right, the frame receives nothing — a live run returned `{"clicked":"@e18","at":[180,305]}` twice while that document's own event log stayed empty. Exits named in the error: the `@d<frameId>.<n>` bridge path, the user's own click, or `tab.create` the frame URL as a top-level tab. Sensing (`read_page` / `find` / `element.info` / `screenshot`) and `select_option` via the frame bridge are **not** refused — they reach those frames. Same-process child frames (cross-origin, same site) keep working on the coordinate path. |
| `srcdoc:` / `about:blank` / `file:` frame | `FRAME_UNREACHABLE` for bridge ops: the content scripts match `http(s)` only, so those frames have no bridge, no input blocker. Perception can still drill in from a same-origin parent via `frame_path`. Closing the input-blocking gap needs a `manifest.json` change — left open deliberately. |
| Several frames with the same URL/identity | `FRAME_AMBIGUOUS` / `REF_FRAME_AMBIGUOUS`: refused, never guessed. |
| A frame ref after its document changed | `REF_STALE` — stale coordinates in a frame are worse than on the top page, so this fails closed. |
| A frame's content bridge stops answering | `BRIDGE_TIMEOUT` (12 s for a normal op, 30 s for the heavy read ops — `getPageText` / `getDomTree` / `search` / `extractData` / `extractSite`) and then a **30 s** cooldown for that `(tabId, frameId)` (it was 5 s, and 5 s never fired in practice: a caller that just burned the full 30 s budget only comes back after those 5 s have elapsed, so `BRIDGE_WEDGED` stayed invisible). During the cooldown the call does **not** blind-reject — it first sends an 800 ms `selfInfo` liveness probe addressed to that frame: no answer → sub-second `BRIDGE_WEDGED` and the window re-arms; the frame answers → the cooldown is dropped and the call runs for real, so a healed frame recovers without a navigation (`dialog.handle` alone is enough). A probe that reports "no listener there" surfaces `BRIDGE_UNREACHABLE`. The bookkeeping is per `(tab,frame)`, which is what the code can guarantee: it bounds the *cost* of a dead frame to ≤800 ms per call instead of a full 30 s. Whether one wedged frame also jams the tab-level channel for its siblings was **not adjudicable offline** (the live run saw a second frame time out too, which is equally consistent with a tab-level jam), so no promise is made about sibling frames — each frame is judged by its own probe. The previous behaviour was every dependent call burning the full 40 s `TOOL_TIMEOUT`, one after another, until the tab looked permanently broken. The record also clears on navigation (`webNavigation.onCommitted/onCompleted`) and on `tabs.onRemoved`. *(offline-proven, awaiting a live re-check)* |
| The shield's veil will not move aside for that frame/point | `SHIELD_PASS_FAILED` — the action was aborted, zero input events were sent. Exits are listed in [Shield and the silent-lie fix](#shield-and-the-silent-lie-fix). |
| `select_option` inside a frame | Works via the frame bridge (`via:'frame-bridge'`, `result.synthetic:true`) — the `change` event is synthetic DOM, exactly like the main-frame `callOnNode` path. |
| iframe loaded while the agent was mid-task | Re-armed through `webNavigation.onCommitted` (`frameId > 0`), but only for tabs the session owns and only in the shield state the top frame actually reports. Frames inserted before any arm and lost to a service-worker restart are picked up by the next `snapshot` resync. The re-arm answers with a verdict rather than silence — `{sent, reason, mode, error}` (`shield_unreachable` / `shield_not_active` / `frame_unreachable` / `storage_unreadable` / `main_frame`), and `background.js` writes that verdict to the audit ring (`action: shield.rearm_frame`), so `ubb audit tail` tells you whether a given frame actually got armed instead of leaving you to guess. |

After reloading the extension, run `ubb frames.probe` once on a page with iframes: it returns the truth table for *this* browser build (per-CDP-frame `Accessibility.getFullAXTree` / `Page.createIsolatedWorld` / `DOM.getFrameOwner` success or error code, bridge reachability, frame pairing, devicePixelRatio).

`frames.probe` is now **read-only in fact, not just in its description.** The live run caught it scrolling the page under the caller (scrollY 2520 → 911 in a single "read-only" probe) and reporting a box composed from frame-chain offsets captured *before* that scroll, which is why the sample came back with a nonsensical `viewport_box.y = -1299`. The coordinate sample now samples with `scroll:false`, the box and the scroll offsets come from the same source at the same moment, and the report carries its own evidence: `checks.page_state_unchanged {unchanged, scroll_moved_in_frames}`, `checks.scroll_y_by_frame {before, after}` per frame, and a `probe_moved_the_page` flag on the sample if it ever moves the page anyway. A negative `y` in the sample is now a *statement about the current scroll position* (off-screen but measured), not a measurement error. Pairing is observable too: `paired[]` rows carry `resolved_by`, `unresolved[]` rows are structured with a reason and the candidate orders, and `checks.window_name_handshake` keeps the **full** error instead of truncating it at 120 characters.

One measured fact worth repeating, because it is a measurement and **not a promise**: on this machine (Edge, 2026-10-28) a cross-site frame's `window.name` handshake was refused by the site's own policy — `Failed to read a named property 'name' from 'Window': Blocked a frame with origin …` — so that page's pairing resolved **positionally (by DOM order)** and the identity channel was unavailable. Whether the handshake works on your browser is exactly what `frames.probe` is for; read `checks.pairing_note` before assuming frame identity is trustworthy on a given page. *(the new probe fields are offline-proven; their behaviour on a live page awaits a re-check)*

## Site rules are data

The six hardcoded extractors (github / zhihu / juejin / wechat / xiaohongshu / twitter) now live in `content/site-rules.json` and are executed by a small op interpreter in `content/bridge.js` (`text / join_texts / images / videos / group / repeat / reset / when`). Adding or fixing a site is **a JSON rule, not a code change, and not an extension reload**:

```bash
ubb site.rules.validate '{"rules":[…]}'   # grammar + selector + executable-key checks, nothing stored
ubb site.rules.add '{"rules":[…],"confirm":true}'   # one rule → chrome.storage.local ("ubbSiteRules")
ubb site.rules.reload                     # re-assemble the service-worker cache
ubb site.rules.list                       # effective set, in match order
```

User overrides are merged **ahead of** the built-ins and win on the same `id`. The packaged file is read by the service worker (`content/` fetch from a content script is blocked by MV3 without `web_accessible_resources`), cached in `lib/bridge-ctl.js`, and attached to each `extractSite` call. Validation hard-refuses any executable key (`eval`, `script`, `function`, `on*`, `html`, `url`, `src`, …) — rules are data, never code. There is no `site.rules.remove` yet: replace a user rule by re-adding the same `id`, or clear the storage key.

## Notes & limits

- **A `SHIELD_PASS_FAILED` is a behaviour change, not just a new code.** Agents that previously saw `{"clicked":…}` / `{"filled":…}` and moved on will now see a throw in exactly the situations where nothing used to happen. That is the intended trade — a red error you can act on beats a green lie — but anything scripted against the old shape should expect the abort, and the correct response is one of the four exits named in [Shield and the silent-lie fix](#shield-and-the-silent-lie-fix), never a blind retry.
- **Five more "the call succeeded but nothing happened" shapes were retired in this batch** (offline-pinned in `test-fill` [8] and `test-integrate` [B]; **offline-proven, awaiting a live re-check**): `screencast.stop` no longer answers `{stopped:true}` when the browser refuses `Page.stopScreencast` — it answers `{stopped:false, reason:"cdp_stop_failed", local_slot_released:true}` and says the tab may still be capturing; `emulate {network:…}` no longer swallows a refused override (and an unknown preset name is refused instead of quietly clearing while reporting success); `emulate.reset` answers `{reset:false, failed:[{step,error}]}` when a step was refused rather than claiming a full reset; `perf.stop` separates "Tracing.end was refused" (`stopped:false, end_error`) from "the flush timed out" (`timeout:true`); `wait_for` counts a failed page read as *no answer*, so an unreadable document can no longer satisfy `element_hidden`. Same rule as the shield gate: a failure has to change the return value. The frame re-arm took the same treatment — `rearmFrame` now always returns a verdict (`{sent, reason, mode, error}`, never a rejection), and `background.js` writes it to the audit ring instead of dropping it in a `.catch(() => {})`, so "did that late iframe actually get armed?" is answerable from `ubb audit tail`.
- **`extension: true` is not a version.** `ubb status` / `/health` now carry `extension_build` (the `BUILD` string from `lib/config.js`, reported by the extension in its `hello`) beside the daemon's own identity. Both halves have to be restarted for it to change: the **extension** via `chrome://extensions` ↻, the **daemon** by killing the old process (it holds its code in memory — one running since 2026-10-26 was still answering `secret.resolve` as an unknown event, which turned a working reverse-RPC path into `SECRET_FETCH_TIMEOUT`). Treat `extension_build` missing → stale daemon, `extension_build` wrong → un-reloaded extension. *Field is wired and verified against a daemon started on a scratch port; seeing it in your own `ubb status` awaits your restart — the currently running daemon still does not show it.*
- Restricted pages (`chrome://`, `edge://`, extension store) are blocked by design, and so are `javascript:` / `data:` / `blob:` navigations. Both ends of the pipeline are closed: `normalizeUrl` no longer launders `chrome://settings` into `https://chrome://settings`, and `isRestrictedUrl` re-checks the scheme-peeled shape as well (the old prepend bug would have walked past the gate).
- **One active session.** `sessions.active()` is a single slot: agents driving the same browser contend for "the last tab". Every targeting tool accepts `tab_id` and you should pass it explicitly; `targetTab()` without `tab_id` mutates session state.
- **Cross-process (OOPIF) frames have no input channel at all** — MV3 exposes no `sessionId`, and a page-level debugger session's `Input.*` cannot be routed into a frame that lives in another process. `upload_file` and `ax.action {action:"setValue"|"expand"}` answer `FRAME_UNSUPPORTED` there, node-based tools without a frame branch (`dropdown_options`, `replay`'s `@eN` fill path — both go through `callOnNode`, and a frame ref carries `backendNodeId: null`) answer `REF_STALE` rather than silently doing something else, and **since this batch so do the coordinate tools**: `click` / `hover` / `fill` / `fill_form` / `form.set`'s physical click / `ax.action {focus|click}` / `drag` / `snapshot {probe_hover}` refuse before putting a single `Input.*` on the wire. What the previous live pass recorded (on the pre-fix build), and what the old docs got wrong: the same call in a **same-process** child frame lands for real (that frame's own log recorded `click isTrusted=true`), while in the cross-site frame of the same tab the tool returned `ok:true` with correct coordinates and the document received **zero events** — "coordinates reach OOPIFs" was a claim the browser had already refuted. Perception (bridge: `read_page` / `find` / `element.info` / `dropdown_options` by `@d` ref / `select_option`) does reach those frames, and the `@d` action path (in-page synthetic events) does too. `srcdoc` / `about:blank` / `file:` frames have no content script at all: no bridge, no shield input-blocking (closing that needs a manifest change).
- **The ref → page-JS path now goes through an object handle, and it is pinned only offline.** `callOnNode` is how a ref reaches page JS at all: `dropdown_options {ref}`, `fill {ref}`, `form.set {select_option}`, `ax.action {setValue}`, `secret.fill`, shadow-tree controls and replay's fill/select steps. It now walks `DOM.getDocument` → `DOM.resolveNode` → `objectId` → `Runtime.callFunctionOn` → `Runtime.releaseObject` (one `getDocument` per document generation, because this browser really does answer `-32007 Document needs to be requested first` otherwise; the handle is released afterwards). It used to send `backendNodeId` straight to `Runtime.callFunctionOn` — a parameter that command does not have — CDP dropped the unknown key, all three identifiers arrived empty, and every one of those calls died with `-32602`; the same broken body was duplicated in `lib/tools-replay.js`. **The chain is nailed against the official parameter table, not against a real tab: the 19:00 live pass was still running the old build, so `DOM.resolveNode` producing a usable handle on your machine is unconfirmed.** Say it plainly as a limit: if `resolveNode` cannot get a handle for a shadow-tree node, the answer is `REF_STALE` ("this Edge build gave no runtime handle for it … in-frame targets act through the bridge/coordinate path") — *not* a quiet downgrade to another path, and *not* a success. So **writing into shadow DOM is not yet a guarantee**, it is a claim awaiting re-check. The `{selector:…}` route goes through `evalJs` and never touched this chain; `SELECTOR_FAILED` still means "shadow DOM needs a ref".
- **One screencast per tab.** `screencast.start` (and therefore `ubb liveview`) holds a single slot per tab; a second holder gets `SCREENCAST_BUSY` naming the current owner instead of silently stealing the stream, and `screencast.stop` only releases it for the matching owner (an agent cast is owned by `agent`, `ubb liveview` by the literal `liveview`; `force:true` is the explicit takeover). Consequence to know: two `ubb liveview` processes share the same owner name, so the one that exits first does stop the other's stream — run one liveview per machine.
- Background tabs are **not** uniformly automatable, and the split is now stated where it bites. What works on a background tab (an agent tab in a window that is not covered by anything else, or a non-active tab of a visible window): screenshots, `snapshot` / `read_page` / `extract` / `find`, `network.*` / `console.*`, `history.*`, downloads, tab bookkeeping, the **bridge paths** (`click {selector}` / `@d` refs, `fill {selector}` / `@d`, `select_option`, `evaluate`, `emulate`) — those go through page JS and are not hit-tested by the browser's input queue. What does **not**: a trusted **pointer or keyboard** action (`click` by ref/coordinates, `drag`, `hover`, `type`, `press_key`, `fill`'s iframe coordinate path, `form.set`'s physical click, `scroll`'s wheel fallback) into a document whose `document.visibilityState` is not `"visible"` — i.e. the Edge/Chrome window is **minimized or covered by another window**. `tab.select` activates the tab and focuses its window and **still leaves such a tab hidden**; only the user putting that window in front changes it. Those calls are refused **before dispatch** with `INPUT_NOT_DELIVERED` and **zero events on the wire** (see [Shield and the silent-lie fix](#shield-and-the-silent-lie-fix)). Cross-site **OOPIF** actions are refused on a separate code (`FRAME_UNSUPPORTED`), visible or not. Still true, and still the reason `active` exists: CSS `:hover` menus, live screencast frames of animated pages and lazy-load-dependent extraction need a *painting* window (`tab.create {"active":true}` / `tab.select`, and `request_help` / `record_start` bring the tab to front automatically); `window.minimize` stops repainting, so screencast frames go still until `window.restore`.
- Service-worker restarts and daemon kills self-heal (session state survives via `chrome.storage.session`; refs do not survive browser restarts). The audit `seq` counter is mirrored into `chrome.storage.session`, so it stays monotonic across a restart — but the ring itself is in-memory and the entries lost during the restart are unrecoverable; `ubb audit tail --follow` is what persists them.
- `download.read` does not exist as a tool: a service worker has no `fs` and `fetch('file://')` is refused. Text downloads are read on the daemon side — `ubb download cat <id>` (three gates: the extension's `text_readable`, a local mime/extension + byte sniff, and a path check that only accepts answered paths inside the download roots; default root `~/Downloads`, extend with `UBB_DOWNLOAD_DIRS` or `--allow-path`). Binaries are refused outright, never base64'd into the conversation.
- `replay` re-matches on role + accessible name from a *fresh* snapshot, so a page that renamed or removed a control answers `MATCH_NOT_FOUND` instead of clicking something nearby; masked `***` values in a trace are refused (re-run with `vars`). Replay steps that need a CDP node inside a frame are not wired to the frame coordinate path yet — those steps stop rather than guess.
- Saved replay scripts live in `chrome.storage.session`: gone when the browser restarts, ≤1MB each, and exported to disk only if you copy them out yourself.
- `record_stop` traces carry selector/text/role/label only — no backendNodeId, no frameId — which is why re-matching is semantic and sometimes needs `start_at` to resume.
- `print_pdf` uses CDP `Page.printToPDF`; `tag_selection` (accessibility tag trees) maps to newer CDP params (`tagSelection`/`displayTags`) and will error on an old browser core — it is opt-in for that reason. Paper sizes are inches, margins centimetres (CDP semantics, not the same units).
- `export.youtube` may be blocked by YouTube's caption enforcement without a logged-in profile; `export.gsuite` requires the user's Google login.
- HTML5 drag & drop lands more reliably with human mode enabled; `replay` reports `drag` events as skipped.
- `batch` (≤12 steps) re-enters the dispatcher, so per-tool timeouts, `confirm` gates, audit and redaction still apply per step; `batch`, `session.stop`, `tab.close` and `human.set` are refused inside it.
- The web console (`console/index.html`) and `console/liveview.html` talk to the extension over `externally_connectable` on `http://localhost` / `127.0.0.1` with the daemon token. That channel reaches the dispatcher directly, so it does not pass the daemon's placeholder substitution point (see [密钥与自动化边界](#密钥与自动化边界) — substitution is skipped there, which means no plaintext is produced).
